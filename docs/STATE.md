## Key decisions (don't re-litigate)

- Drive official CLIs; files are source of truth; saved-plan-only apply. (ADRs 0001–0003)
- Cloud connection is bound **per environment**, never on the project. (ADR-0005)
- Versions are per-project, deployed independently per environment. ([20](20-pipelines-deployments.md))
- Theme is **Dark + Light only** (no System); Dark default.
- DB schema now via **EF migrations**. `AppInitializer` is upgrade-safe and never requires a reset: a migration-controlled DB gets pending migrations applied; a **legacy `EnsureCreated` DB is adopted** (missing model tables created + migrations stamped as applied); a fresh/empty DB is created from migrations; and with no migrations authored it falls back to `EnsureCreated`. Files are source of truth; the file-history store is a recovery cache (dedup by SHA-256, GZip). In-app delete of tracked files is **off by default** (Settings → Security); external deletes are detected and recoverable.
- Terraform engine lives **in Infrastructure** (not a separate `Fenrix.IaCStudio.Terraform` project yet) to match the Phase 2 precedent and avoid a blind `.csproj`/`.slnx` change. Commands run via **`ArgumentList` only** — never a shell string. The **preview and the executed process share one argument list** (`TerraformCommandCatalog`), so they can't diverge. Redacted history is persisted (`CommandRun`); raw output goes to `Logs/terraform/<runId>.log`, never the DB.
- On **SQLite**, all `DateTimeOffset` columns use `DateTimeOffsetToBinaryConverter` (SQLite can't `ORDER BY`/compare `DateTimeOffset` in SQL); applied via `ConfigureConventions`, guarded to SQLite only. If you change this, regenerate the migration.
- **Apply only the exact saved plan** (ADR-0003): `plan -out` → `show -json` (parsed in memory, redacted, never persisted raw) → `apply -json <plan>`. Every plan is its own file so any reviewed plan stays applyable. Destroy = `plan -destroy` then apply; drift = `plan -refresh-only`. A plan is **invalidated** when the config or provider-lock hash changes after creation.
- Everything for a project stays **inside the project folder**: plans in `plans/<env>/`, env locks in `.fenrix/locks/`. Plans, state (`*.tfstate`), and the provider lock are **version-controlled** (git + Fenrix file history) — Ivo's call; repos must be private because plan/state files carry plaintext secrets. Locks are the exception (ephemeral, gitignored).
- Per-environment **operation lock** is an on-disk lock file (`FileEnvironmentLockService`): exclusive-create is the lock, PID recorded for staleness/force-release; only one state-changing op per env; read-only `show` doesn't lock.
- **Git engine lives in Infrastructure** (like Terraform), driving the official `git` CLI via the shared **`ArgumentList`** runner — never a shell string. `GitCommandCatalog` is the single source of the argument list, so the preview and the executed command can't diverge. **Read-only** queries (status/log/diff/branch/stash/rev-parse) run *silently* (no history row) so frequent UI refreshes don't spam history; **mutations** (init/clone/stage/commit/fetch/pull/push/branch/merge/stash-write) go through `GitProcessCoordinator` and are recorded as redacted `CommandRun` rows (`Tool=git`) + `Logs/git/<runId>.log`. Repo detection uses `rev-parse --show-toplevel` (supports a project nested in a larger repo), but `git init` targets the project root. Remote credentials in URLs are redacted in previews/history (`GitUrlRedactor`). To avoid a DI cycle (`GitService` depends on `IProjectService`), project-creation init uses the narrow `IGitRepositoryInitializer`.
- `-json` command output (`show`/`apply`) is **never written to a log file** (it can contain unredacted sensitive values); only the human-readable `plan` run is logged (Terraform already masks sensitive there). Redacted history rows are still recorded for all runs.
- **Advanced Git (Phase 6) added no new services, no new DI, and no DB migration** — everything hangs off `GitService` + `GitCommandCatalog` (still the single `ArgumentList` source, so preview == execution). **Interactive rebase is driven non-interactively**, never a shell string: a temp todo file is copied over git's todo via `GIT_SEQUENCE_EDITOR="cp <todo>"`, `GIT_EDITOR=true` keeps default/combined messages, and reword uses `pick` + `exec git commit --amend -F <msgfile>` so no editor blocks. This relies on git's bundled shell providing `cp` (true for Git-for-Windows); if that ever changes, swap the sequence editor for a tiny bundled helper. **Line staging never shells `add -p`** — `GitPatchBuilder` reconstructs a minimal unified patch of the selected lines (unselected opposite-side changes downgraded to context, hunk headers recomputed) and applies it with `apply --cached [--reverse]`; validated against real `git apply`. Sequencer state (merge/cherry-pick/revert/rebase in progress + conflicts) is derived from git-dir marker files, not parsed from stderr.

- **Provider integrations (Phase 7) are thin adapters behind `IRepositoryProvider`**, driving official **REST APIs via raw typed `HttpClient`** (no vendor SDKs, no new NuGet beyond `Microsoft.Extensions.Http`) — Ivo's call, to keep `.csproj` churn minimal and match the fixture-based contract-test approach. Adapters **never throw for expected failures**; they return `ProviderResult<T>` with a typed `ProviderErrorKind` (auth/404/rate-limit/network) so the UI gives precise guidance. When no adapter matches a remote, the factory falls back to `GenericGitProvider` (capabilities `None`) and core Git still works. **Secret story pulled forward from Phase 8** (Ivo's call): repository tokens live in the **Windows Credential Manager** (P/Invoke), SQLite stores only a `SecretReference`; the token is resolved just-in-time into a transient `ProviderConnectionContext` and never persisted/logged/redaction-exposed. **AWS CodeCommit** stays minimal this phase — it authenticates with IAM/SigV4/`git-remote-codecommit`, not a PAT, so its host API belongs with the Phase 8 AWS cloud-connection work; Git clone/push against CodeCommit still works via the credential helper. Full cloud sign-in (Azure/AWS/GCP) + per-environment binding remain Phase 8.

- **Deployments (Phase 9.5) are a view + a thin governance layer over the Phase 4 spine, never a new apply path.** A `Deployment` row is written by the **single `IDeploymentRecorder`**, invoked *inside* `TerraformApplyService` after a successful apply — so the board is accurate whether you deploy from the Plan & apply page or the Pipelines flow, with no double-recording (idempotent per saved plan). The recorder **resolves the `ProjectVersion` from the plan's Git commit** (creating an implicit version for ad-hoc applies), and reads the state pointer **only** as the two non-sensitive top-level fields (`serial`/`lineage`) of the local `terraform.tfstate` (never resource values, never logged). Governed deploy is **plan → gates → apply the exact saved plan** (`DeploymentService` orchestrates `ITerraformPlanService` + `ITerraformApplyService`); it first **checks the version's commit out** (clean trees only) so what deploys is what was cut — otherwise the RepositoryAtVersion gate blocks with a one-click checkout. The **approval gate is a local self-ack** (a checkbox that must be ticked); real multi-user role-based approvers stay Phase 11. **Fan-out is not a transaction** — it auto-applies gate-clean targets and flags approval/production targets as "needs confirmation" to finish individually. Pipeline definitions are **optional** (one per project); a project without one still deploys per-environment from the Matrix. `ProjectVersion`/`Deployment` tables already existed (Phase 4 `AddSavedPlans`), so the only new migration is the two **pipeline-config** tables (`AddDeploymentPipelines`). — Ivo's calls (one big batch; record on both paths; capture serial/lineage; local self-ack).
- **Managed key material (Phase 8.5) is Fenrix-specific, so it uses DPAPI (item 6 of docs/11).** Private keys are stored **encrypted at rest** under `<dataRoot>\Data\keys\<projectId>\` — outside any project folder, never git-tracked; the DB holds only a `KeyPair` metadata row + a `SecretReference`. **Import never decrypts the private half**: the public key + fingerprint come from the public blob embedded in OpenSSH/PPK files, or from `System.Security.Cryptography` for RSA/EC PEM; the raw bytes are DPAPI-encrypted verbatim and round-trip exactly on export. **Generation captures the private key from Terraform outputs** (`tls_private_key`) parsed in memory (`captureLog:false`, never the redacting parser), in a self-contained throwaway working dir — a `KeyPairGenerateApply` kind deliberately outside the saved-plan-only-apply rule (that rule governs applies to real project state; here there is no backend/state-of-record). The optional AWS register path adds `aws_key_pair`, composes a bound environment's connection for creds, and **keeps** its working dir (state carries the private key, so it lives under the protected data root, never the project) so the cloud object can be de-registered (`destroy`) on delete/rotate. **Dependency-free by choice** (Ivo's call — no BouncyCastle): unencrypted-RSA PPK converts to PEM on import; encrypted/non-RSA PPK conversion + Ed25519-from-bare-PEM derivation are deferred (keys still import + store, public shown when derivable). **Export is gated + audited**: off by default behind `security.allowPrivateKeyExport`, AND requires typing the key name, AND every reveal/denial writes a redacted `CommandRun` audit row (never the key itself).
- **Cloud connections (Phase 8) are the single source of auth for a run.** The connection (created once in the hub) holds everything an environment needs; you bind it per environment and Terraform uses it — there is **no separate "sign-in" step in the Terraform area** (Ivo's call). Adapters (`ICloudConnectionProvider`, mirroring `IRepositoryProvider`) **drive the official CLIs** (`az`/`aws`/`gcloud`) through the shared `ArgumentList` runner — never a shell string; `CloudCli` resolves PATH+PATHEXT and routes `.cmd` shims via `cmd.exe /c` (still argv, safe for space-free args). Fenrix **never becomes the credential custodian**: it composes process-scoped env vars (`ARM_*`/`AWS_*`/`GOOGLE_*`) at execution time and leans on the tool-native stores (az cache, AWS profile/SSO, gcloud ADC); the only Fenrix-held secret is an **Azure service-principal client secret** in Windows Credential Manager, resolved just-in-time and never persisted/logged (history stores redacted args only, never env vars; the preview redacts sensitive env chips). The cloud connection is bound **per environment** (never per project); a **state-changing op is blocked** (authentication-required) when the environment is unbound. **Phase 8 needs NO new migration** — `ProjectEnvironment.CloudConnectionId`, `CloudConnection.{Client,MetadataJson,LastStatus,LastTestedAt}`, and the secret backbone all already exist.

- **Visual builder (Phase 10) authors config, never state; files stay the source of truth.** Provider schemas come from `terraform providers schema -json` (read-only, no lock, not cloud-gated; needs `init` to have run) and are **cached offline** per project+environment under `Cache/terraform-schemas/` (raw JSON + a metadata sidecar with the provider-lock hash for a staleness hint) — the builder then works without re-invoking Terraform. Generation is **pure** (`ConfigHclBuilder` + `HclEmitter`, canonical 2-space HCL); persistence is the **only** side of it that touches Infrastructure and it goes through the **same atomic-write + file-history path as the editor** (`IFileTreeService.WriteFileAsync`) — new blocks are appended, and **existing simple blocks are edited via in-place value-span splices** so every comment, complex expression, and nested block is **preserved byte-for-byte** (the deliberate doc-07 limitation: the builder models literals, everything else round-trips as raw).
